# AGENTS.md

Обязательные правила для любого AI-агента (Claude Code, Codex и других),
работающего с проектом «Система прогнозирования положения воздушного объекта»
(магистерская диссертация, модель TATPN). Читается всегда, целиком.

Подробности не здесь: план, состояние, эксплуатация вынесены в `md/`. Загружать
их все сразу нельзя - см. таблицу маршрутизации в конце.

## Границы workspace

| Что | Режим |
|---|---|
| `config.py`, `run_*.py`, `demo.py`, `status.py`, `benchmark_gpu.py`, `data_processing/`, `data/`, `eval/`, `baselines/`, `features/`, `models/`, `training/`, `visualization/` | изменяемый |
| `README.md`, `md/`, `ИНСТРУКЦИЯ_ЗАПУСКА.txt`, `AGENTS.md`, `CLAUDE.md` | изменяемый (документация) |
| `flight_logs_source/` | **read-only**: исходные логи, единственный источник реальных данных |
| `не надо/` | **read-only** архив прежней монолитной реализации, не импортировать, только как справочник |
| `.venv/`, `processed_data/`, `artifacts/`, `logs/`, `reports/`, `flight_logs_generated/` | генерируется запуском этапов, в git не хранится, руками не править |

Два компьютера. Агент работает на **рабочем ПК** (Windows 10, без GPU) и не имеет
доступа к **домашнему ПК** (Windows 11, RTX 5070 Ti), где идёт обучение. Данные об
обучении на GPU агент получает только из того, что прислал пользователь
(`summary.txt`, вывод `status.py`). Не оценивать GPU-метрики и время на глаз и не
выдавать числа с CPU за числа с GPU. Подключение и ежедневный порядок - в
`md/DAILY_ROUTINE.md`.

## Git

По умолчанию разрешены **только команды чтения**: `status`, `diff`, `log`, `show`,
`branch --list`. `commit` и `push` - только после явной просьбы пользователя в
текущей сессии; одобрение одного коммита не распространяется на следующие.

- `--force`, `reset --hard`, переписывание истории, удаление веток - только по
  явной просьбе. Решение пользователя: принудительную перезапись удалённой ветки
  по умолчанию не предлагать и не выполнять.
- Незакоммиченные изменения в рабочем дереве считать пользовательскими: не
  откатывать, не перезаписывать целиком, не «приводить в порядок» заодно.
  Пользователь правит файлы параллельно с агентом: перед правкой перечитывать файл
  и не возвращать то, что он убрал.
- В коммит добавлять файлы по именам, а не `git add -A`, если в дереве есть
  чужие или не относящиеся к задаче изменения.
- Не коммитить: `.venv/`, `processed_data/`, `artifacts/`, `logs/`, сгенерированные
  HTML-отчёты по всем траекториям. GitHub не принимает файл больше 100 МБ, такие
  файлы однажды сделали репозиторий неотправляемым (~900 МБ).
- Сообщение коммита - на русском, в PowerShell передавать через файл (`git commit -F`):
  многострочное сообщение с кавычками в аргументе разбивается.

## Зависимости и запуск

- Не добавлять библиотеки и не менять `requirements.txt` без согласования.
- Обучение этапов 3-5 на рабочем ПК не запускать: это часы на процессоре, а
  результат не пойдёт в работу (в диплом идёт только GPU-профиль). Допустимы
  быстрые проверки: `py_compile`, смоук-тест forward/backward на малых тензорах,
  этапы 0-1.
- Не выдавать `py_compile`, чтение кода или смоук-тест за проверку обучения. Если
  проверка не выполнялась - прямо это сказать.
- Пока на домашнем ПК идёт `run_all.py`, изменения скриптов этапов, `models/`,
  `training/` и `data_processing/` не должны попадать на домашний ПК: каждый
  следующий этап читает свой файл в момент запуска, и правка изменит условия
  посреди цикла или остановит его. Правки на рабочем ПК допустимы, но не
  пушить и предупредить пользователя, что `git pull` дома - только после цикла
  (либо после его остановки).
- Не удалять данные, чекпоинты и файлы вне перечня «генерируется» без явного
  разрешения. Не менять внешнее состояние (сеть, чужие машины) без разрешения.

## Правила кода

- Сохранять стиль ближайшего файла: именование, форматирование, структуру,
  манеру комментариев. Не менять стиль без просьбы. Отступ 4 пробела.
- Читаемость, DRY и разумный KISS. Массовый рефакторинг соседнего кода - только
  отдельной задачей.
- Комментарии редкие и короткие, только про неочевидный контракт или причину
  решения. В начале модуля - docstring на русском: назначение и что проверяется.
- Тексты, комментарии, документация - на русском, короткое тире (дефис), без «—».
- **Параметры - в `config.py`.** Настройки, зависящие от устройства (CPU/GPU:
  окно, батч, эпохи, lr), - в начале `run_stageN.py`. Не размазывать числа по коду.
- **Воспроизводимость.** Все случайные процессы - от `config.RANDOM_SEED`. Не менять
  порядок обращений к генератору случайных чисел в данных и разбиении
  без согласования: сломается сравнимость этапов.
- **Разбиение - только `data_processing/splits.py`, метки в датасете.** Реальные
  полёты делятся до аугментации, расширенные траектории порождаются только из
  полётов своей выборки (иначе производные от одного полёта попадают и в train, и
  в test). Не пересчитывать перестановку в этапах: читать `load_splits()`.
- **Метрики - только из `eval/metrics.py`**, определения единые для всех этапов.
  Не копировать их в скрипты этапов.
- **Нарезка окон - только `data/windowing.py`** (хвост наблюдения + смежный
  future). `data_processing/dataloader.py` содержит известный баг нарезки и
  прежнее разбиение с утечкой; для обучения не используется.
- **Оценка (val/test) - всегда без teacher forcing.** Train-метрики с teacher
  forcing не сравнивать напрямую с val.
- **Инкрементальность.** Один новый компонент за этап, в новых файлах; прежние
  этапы целиком не переписывать. Каждый этап: overfit-one-batch, бейзлайн в
  таблице, `history.json` + `summary.txt`, проверки в сводке.
- **Аугментированные траектории физически согласованы:** время - по фактической
  длине пути, скорость в диапазоне `AUG_SPEED_RANGE`, отбраковка по `AUG_*` в
  `config.py`. Растягивая пространство, всегда масштабировать время (иначе
  скорости в км/с, и несколько сотен таких траекторий определяют все метрики).
  После любой правки генераторов проверять скорости по типам траекторий.
- **Реальные логи - только из `flight_logs_source/`**, с дедупликацией по имени.
  Не возвращать чтение внешних копий папок: каждый полёт учитывался дважды, и
  один полёт попадал в train и в test.
- Не подставлять числа в документацию без источника: брать из сводок и вывода
  этапов.

## Поиск ответов

Сначала искать ответ в коде, истории Git, логах этапов и уже написанной
документации. К пользователю идти только с существенной оставшейся
неоднозначностью, которая меняет результат работы.

Писать код и документацию так, чтобы следующий агент понял их без скрытого
контекста этой сессии.

Отвечать кратко. Критически проверять и решение пользователя, и своё: если видно,
что предложенный путь ведёт к проблеме, сказать об этом до того, как писать код.

Вопросы, на которые пользователь должен ответить, выносить в конец ответа
отдельным выделенным блоком (заголовок «Нужен ваш ответ», нумерованный список),
а не растворять в тексте - иначе их не замечают.

## Рабочий протокол

Перед изменением кода:

1. Прочитать `md/PROJECT_STATE.md`.
2. Посмотреть `git status` и относящийся к задаче diff - только на чтение.
3. Прочитать нужные тематические документы и исходники, не все подряд.
4. При конфликте документации с кодом доверять коду и исправить документацию.

После изменения кода:

1. Просмотреть diff и выполнить проверки, соразмерные риску (см. ниже).
2. Обновить `md/PROJECT_STATE.md` как снимок текущего состояния, а не журнал.
3. Устойчивое неочевидное знание записать в подходящий тематический документ,
   удалив устаревшее и не дублируя текст.
4. В финальном ответе назвать результат, затронутые файлы и то, что не проверялось.

Отдельно: если правка сделала неверным кусок `README.md`, `AGENTS.md` или файлов
в `md/` - исправить его в том же ответе, а не «потом».

## Проверка изменений

Код:

1. `py_compile` затронутых файлов;
2. для моделей - смоук-тест forward/backward на малых тензорах (формы выходов,
   loss считается, градиенты идут);
3. для логики данных и метрик - проверка на подставных данных с известным ответом.

Результат этапа (по присланной сводке) читать так:

1. `overfit_one_batch` и «модель обучилась» - обязательные; цели этапа (обогнать
   линейную экстраполяцию и т.п.) - научный результат, не блокируют;
2. сравнивать с бейзлайнами на **том же** горизонте и том же датасете;
3. смотреть разрыв `train_ADE` и `val_ADE` (перетренировка) и RMSE рядом с ADE
   (выбросы).
